# Правила проекта SuperLinker

> Этот файл — единый источник правил. **Перед каждой задачей** ассистент сверяется с ним и следует ему без исключений.

---

## 1. Режим работы

| # | Правило |
|---|---------|
| 1.1 | **Без явного приказа — ничего не делаем.** Не пишем код, не меняем файлы, не запускаем команды, пока заказчик не сказал «делай» / «приступай» / «утверждаю план». |
| 1.2 | Работаем **пошагово**: одна задача → результат → ожидание следующего приказа. |
| 1.3 | Перед началом задачи — **прочитать этот файл** и `docs/ПЛАН-ДЕЙСТВИЙ.md` (если план утверждён). |
| 1.4 | После каждого изменения — **запись в** `docs/ЖУРНАЛ-ИЗМЕНЕНИЙ.md`. |

---

## 2. Язык и документация

| # | Правило |
|---|---------|
| 2.1 | Вся **документация** — на **русском** языке. |
| 2.2 | Весь **код** снабжается **комментариями на русском**, объясняющими логику и неочевидные места. |
| 2.3 | Сообщения в интерфейсе (кнопки, подписи, ошибки) — на **русском**. |
| 2.4 | Имена переменных, функций, файлов — на **английском** (общепринятая практика разработки). |

---

## 3. Планирование

| # | Правило |
|---|---------|
| 3.1 | После описания идеи ассистент составляет **`docs/ПЛАН-ДЕЙСТВИЙ.md`** с пошаговым планом. |
| 3.2 | Разработка **не начинается**, пока заказчик не прочитал план и не написал **«утверждаю»** (или дал правки). |
| 3.3 | Изменения в утверждённый план вносятся только по согласованию с заказчиком. |

---

## 4. Качество и безопасность изменений

| # | Правило |
|---|---------|
| 4.1 | **Ничего не ломать** при правках: минимальный diff, не трогать несвязанный код. |
| 4.2 | Перед сдачей задачи — проверить, что существующий функционал не сломан. |
| 4.3 | Не коммитить секреты (`.env`, ключи, пароли). |
| 4.4 | Коммиты создавать **только по явной просьбе** заказчика. |

Ассистент выступает как:

- **Senior Backend-разработчик** (10+ лет опыта)
- **Бизнес- и системный аналитик**
- **Product Owner** IT-продуктов

При планировании предлагать улучшения с точки зрения продукта, архитектуры и UX.

## 6. Инфраструктура и хранение данных

| # | Правило |
|---|---------|
| 6.1 | Репозиторий на **GitHub**; публичный релиз на другие платформы — **только по решению заказчика**. |
| 6.2 | База данных — **SQLite** (файл на диске). На Railway — **Volume** `/app/data`. |
| 6.3 | **Хостинг — Railway** (автодеплой из GitHub). GitHub Pages не используем. |
| 6.4 | **Без pip/npm-зависимостей** — Python stdlib + vanilla JS/CSS. |
| 6.5 | Пароли и секреты — только в переменных Railway / локальный `.env` (не в Git). |

## 7. Функциональные требования (утверждённая идея)

### 7.1 Сокращение ссылок
- Пользователь вставляет длинную ссылку → нажимает кнопку → получает короткий адрес.

### 7.2 Статистика
- Просмотр статистики переходов по каждой сокращённой ссылке.
- График: ось X — дни, ось Y — количество визитов.
- Скачивание **CSV** с каждым переходом по конкретной ссылке.
- При каждом переходе записывается **IP-адрес** посетителя.

### 7.3 Админка
- Кнопка **«Сгенерировать тестовые данные»** за последние 30 дней.
- Кнопка **«Очистить тестовые данные»**.

## 8. Предложенные дополнения к правилам (рекомендации ассистента)

> Заказчик может принять, изменить или отклонить каждый пункт.

| # | Дополнение | Зачем |
|---|------------|-------|
| 8.1 | **Definition of Done**: задача считается выполненной, когда код написан, прокомментирован, проверен вручную, запись добавлена в журнал изменений. | Единый стандарт «готово». |
| 8.2 | **Одна задача = один логический блок** в журнале изменений (дата, что сделано, какие файлы затронуты). | Удобный аудит истории. |
| 8.3 | **Резервная копия БД**: перед деструктивными операциями (очистка тестовых данных, миграции) — копия файла БД в `data/backups/`. | Защита от случайной потери данных. |
| 8.4 | **Маркировка тестовых данных**: поле `is_test = true` в записях кликов, чтобы очистка не затронула реальную статистику. | Безопасная генерация/удаление тестов. |
| 8.5 | **Приватность IP**: хранить полный IP только если заказчик явно согласен; иначе — хэш или маскировка последнего октета. | Соответствие базовым требованиям приватности. |
| 8.6 | **Валидация URL**: не сокращать не-HTTP(S) ссылки, javascript:, data: и т.п. | Безопасность сервиса. |
| 8.7 | **Версионирование API/схемы БД**: при изменении структуры — миграция с записью в журнал. | Предсказуемые обновления. |
| 8.8 | **Локальный запуск документирован** в README: как установить, запустить, открыть админку. | Быстрый онбординг. |
| 8.9 | **Структура папок фиксирована** в плане и не меняется без согласования. | Порядок в репозитории. |
| 8.10 | **Спорные решения** — сначала вопрос заказчику, потом код. | Меньше переделок. |
